# Strategy, Viability & Risk

**Verdict up front:** This is an unusually well-engineered project pointed at a market of approximately one — and that's fine, *if* the owner is honest that the customer is NNVP and the browser-training pipeline, not the Python ML public. As "yet another CPU backend for Keras," it has no adoption story: Keras users already have four faster, supported backends, and tinygrad users are the demographic least likely to want Keras. The genuine differentiator is the unproven link: tracing a Keras train step on tinygrad's NULL device and exporting it as a WebGPU runner. Everything else — the 99.9% test tally, the import hook, the upstream drafts — is either enabling infrastructure for that, or credibility-building. Priority one is not more op coverage; it is (1) committing and publishing the uncommitted work, and (2) the M0 spike that decides whether this is a platform or a curiosity.

## 1. Viability and adoption

**Who is this for?** Three candidate audiences, honestly weighed:

- **NNVP** (the owner's visual Keras editor with in-browser training). This is the real customer. The design doc (`nnvp-keras-tinygrad-design.md`) is explicit: the Keras/Python emitter becomes the semantic source of truth, Keras becomes the *model compiler*, and a JS loop becomes the trainer, replacing a tfjs engine that has been frozen for 21 months. This is a coherent succession plan with a named milestone.
- **Keras users wanting tinygrad.** Thin. On CPU this backend is slower than jax/tf/torch (generic RNN scan, eager test/predict paths, linalg in float64), and those backends are supported by teams. The one honest pitch — tiny dependency footprint, `pip install` next to the stock wheel, no fork — is nice but not a migration driver.
- **tinygrad users wanting Keras.** Nearly empty. That community's culture (line budgets, minimalism, hostility to abstraction) is close to the opposite of Keras'.

**The plugin-API question.** The docs read keras#23193 correctly, and it is the decisive datapoint: a complete, training-capable MLX backend with ~12,700 green tests was closed unmerged — CLA friction, rolling conflicts across the hardcoded dispatch sites, a meaningless codecov fail, and no maintainer appetite to review 8k lines. The lesson the project drew is right: **the in-tree backend path is dead; do not attempt it.** The entry-point proposal (`keras.backends` setuptools group resolving the same six touchpoints) is the correct *ask*, and the plan to raise it as a design issue referencing Chollet's criteria in keras#20793 — rather than a cold PR — is the correct *process*. But be sober about odds: the same team that let #23193 die has shown no urgency about out-of-tree enablement, and a plugin API is a maintenance commitment they'd be accepting on behalf of backends they don't control. Call it a minority-probability, long-timeline bet. The saving grace is that **the import hook makes the bet non-blocking**: the package works today against stock 3.15.x, fails loudly on anything else, and an eventual entry point merely deletes the hook. The hook is the product; the entry point is upside.

One under-appreciated asset here: the six-touchpoint contract surface documented in architecture.md *is* the plugin API spec, empirically derived and battle-tested. If the design issue is ever raised, that document is the strongest exhibit in it — stronger still if a working browser demo exists as the "here is what out-of-tree backends unlock" argument. Sequence accordingly.

## 2. Maintenance economics

One person, ~9.3k lines of backend plus a 215-line source-patching loader, against two upstreams with very different failure modes:

- **Keras releases** break the *loader*: six exact-match anchors pinned to 3.15.x. The loud-fail anchor design is exactly right — silent breakage is converted into explicit per-version validation work — but it converts every Keras minor release into a mandatory chore: re-verify anchors, re-run the referee, bump the pin. At Keras' release cadence that's a recurring tax of perhaps a day per release, forever, or the package rots visibly (`keras>=3.15,<3.16` means the package is *advertised* as stale the day 3.16 ships).
- **tinygrad 0.x** breaks the *backend*: 0.13 is pinned, the monkeypatch set is closed and guarded (invariant 6), but tinygrad churns internals aggressively and the NNVP path additionally vendors `export_model`. Each tinygrad bump is a full referee re-run plus potential internal-API chasing.

**Sustainable scope for one maintainer:** the project has already done most things right — invariants written down, Keras' own suite as the referee, executable tutorial, `sync_vendor --check`, CI on uv+make. What is *not* sustainable is continuing to expand the surface. The remaining tails (fused RNN kernels, sparse/ragged, TF-string layers, complex arithmetic) should stay exactly where they are: declared out of scope, loud. The unique/vectorize memo's own recommendations are correct — take option (b) (stay loud) for `unique` unless NNVP demonstrates a need, and permanently loud for `vectorize`; the coverage delta is two tests and the honesty cost of (a) is an invariant amendment nobody is asking for.

Two structural suggestions: **(i)** the dual source-of-truth (keras clone + vendored `_backend/`) is justified while the referee runs in-tree, but the referee *could* run against stock keras + the hook, which would test the shipped artifact directly and eventually let the clone demote to a scratch environment. Worth a spike. **(ii)** Everything is uncommitted, spread across a workspace with what look like manual backup copies (`keras-bak-1..4`, `keras-tinygrad-pkg-1..3`). For a project whose entire value is currently reproducible-but-unpublished, that is the single largest risk on the board and costs nothing to fix.

## 3. The upstream PR strategy

**Keras test-side bundle: well-chosen, submit it.** All three fixes are genuinely backend-agnostic and the PR body proves it without needing tinygrad to exist: `test_cross` is broken on *stock keras + numpy ≥ 2.5 on the numpy backend itself* (with a verified companion fix for the numpy backend's own `cross` held in reserve — smart: offer it in the PR conversation, don't presume); the `trainer_test.py` fix is a clean don't-duplicate-dispatch argument; the float8 skipif honestly names the test harness, not the backend, as tf/jax/torch-only. Dropping the ViewAsComplex skipif after the backend started passing those tests was the right call and shows the discipline holding. Risks are small: the float8/trainer fixes telegraph "an out-of-tree backend exists," which is fine — #20793 contemplates exactly that — and the worst case is a polite close having cost a day. The real value is contributor credibility banked ahead of the entry-point conversation. One tactical note: `test_cross` has standalone urgency (every CI environment resolving numpy 2.5 hits it); if the bundle stalls, split it out — it is the fix most likely to be merged fast on its own merits.

**tinygrad PRs: technically well-chosen, procedurally the riskiest thing in the plan.** The sequencing in the draft (PR A dunders → argfix one-liner → slice bounds → issue-then-PR for `__bool__`) is exactly right for that repo's culture: torch/numpy-parity arguments, +8 lines against their own `sz.py` budget, a real downstream consumer, and correctly refusing to cold-PR the reversal of a maintainer's deliberate `__bool__` ban. The self-assessed odds (60–70% for A, 15–25% for B) seem honest. But the process constraint the docs themselves flag is decisive: **tinygrad closes and may ban AI-looking code from new contributors, and this entire codebase is AI-built.** Disclosure is mandatory and disclosed AI-assisted patches from a first-time contributor carry a heavy discount regardless of quality. The owner must rewrite these patches in his own hand, understand every line well enough to defend it live, and expect rejection anyway. Budget accordingly: these PRs are worth one attempt each, not a campaign. The backend-side workarounds (the `tuple(...)` normalizations; RandomCrop staying red) are livable indefinitely — do not let upstream tinygrad acceptance become a dependency of anything.

## 4. The NNVP/WebGPU angle — the actual differentiator

Yes. Without it, this project is a beautifully built answer to a question few people ask. With it, it is something nothing else offers: **full Keras 3 — real Keras semantics, the actual library, cyclic-graph emission included — compiling to a self-contained WebGPU training loop in the browser**, with tfjs (frozen since ~2024) as the incumbent it replaces. The design doc is clear-eyed about this: Keras runs under Pyodide with ~200 lines of stubs, the trace→WebGPU runner pipeline is proven for a hand-rolled MLP, and exactly one link is unproven — capturing a Keras `train_step` (forward + `loss.gradient` + `optimizer.apply`, Python state excluded) as a single exportable schedule on the NULL device. The recently landed `_TrainStepJit` materially de-risks this: the train step is already demonstrably capturable by TinyJit with pinned-buffer weight propagation and bit-for-bit eager parity, which is most of the shape `export_model` needs. It is not the same as a NULL-device export (JitError hazards, optimizer-state buffer enumeration, version-lock on vendored `export_model`), but the distance shrank from "unknown" to "plumbing plus unknowns that are named." The payload/latency numbers (~30–40 MB cold, 20–30 s cold start, 3–8 s retrace) confine this to an opt-in engine — the doc already says so — which is the right product posture.

The strategic point: **M0 is the project's valuation event.** If it works, the 99.9% test tally stops being a vanity metric and becomes the warranty on a unique capability, and the entry-point pitch to Keras gains its killer demo. If it fails structurally, the honest fallback position is "solid hobby backend plus a handful of upstream fixes" — still respectable, but a different project. Either outcome is worth knowing soon and cheaply.

## 5. What to do next, in order

1. **Commit and checkpoint everything, today.** The clone's backend, this repo, the tinygrad patch. Then publish the repo and claim the PyPI name (publishing ≠ promoting; an unclaimed name is pure downside risk). Everything else on this list assumes the work can't be lost.
2. **Run the M0 spike** (Keras Dense MLP from NNVP's generated Python → NULL-device TrainStep trace → exported WebGPU runner → JS loop drives loss down). Standalone page, no app integration, per the design doc. Timebox it; if the trace fights the trainer's eagerness, stop and write findings rather than restructuring the backend.
3. **Submit the keras test-side PR** (or `test_cross` alone if velocity matters). Cheap, standalone value, banks credibility.
4. **tinygrad PR A + the argfix one-liner**, after a genuine human rewrite pass and with explicit AI disclosure. One attempt each; accept rejection gracefully — the monkeypatches are a fine steady state.
5. **Close the unique/vectorize decisions cheaply**: (b) stay loud for both, revisit `unique` only on demonstrated NNVP need. Do not spend on fused RNN kernels or eager-path JIT until something measurable demands it.
6. **Defer the entry-point design issue** until the test-side PR has landed and, ideally, an M0 demo exists. Raise it as a discussion with the six-touchpoint contract and the working hook as exhibits, framed as "make #23193 impossible to repeat," not "merge my backend."
7. **Automate the release tax**: a CI job that runs `--self-check` against the latest keras wheel (and a canary against master) so anchor drift is known the day it happens, not when a user hits the loud ImportError.

## 6. Honest overall

Is this a good project? **As engineering: yes, unambiguously.** The methodology — numpy backend as semantic reference, Keras' own suite as referee, no silent fallbacks in differentiable paths, exactly-once patch anchors that fail loud, invariants updated in the same diff that moves a boundary, an executable tutorial that caught a real regression — is staff-level discipline that most funded teams don't maintain. The documentation is the best part of the codebase, which for a one-person project against two churning upstreams is exactly the right place for it to be.

**What's genuinely novel:** the meta-path import hook that grafts a backend onto plugin-less stock Keras with exactly-once anchors (a technique with reuse value beyond this project); being the first Keras-3-on-tinygrad backend at all; the custom-gradient tape hand-composing VJPs over `Tensor.gradient`; the JIT'd train step with pinned-buffer weight propagation; the complex-lite interop tier; and — if M0 lands — the Keras-as-model-compiler browser training pipeline, which nothing else in the ecosystem does.

**What's commodity:** the large majority of the 9.3k lines — mechanical numpy-to-Tensor op ports whose count (5,500 green ops/numpy tests) is impressive as a QA artifact but is exactly the kind of surface any competent effort would eventually grind out, and exactly the surface that generates the perpetual maintenance tax.

**The risk to name plainly:** this is a bridge between two communities, built to a standard neither demanded, whose default fate — absent the WebGPU story — is to be admired and unused, decaying one Keras release at a time. The project's own documents contain the antidote: HANDOFF's decision queue puts NNVP M0 last, but strategically it is first. Ship the commit, run the spike, and let the result decide how much of the rest deserves feeding.
